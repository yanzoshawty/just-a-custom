## Findings

### 1. [Medium] Storage flooding: per-instance in-memory rate limit, no global cap on inserts

**Files:** `src/app/api/builds/route.ts:10-24`, `supabase/migrations/0001_builds.sql:12-27`
**CWE:** CWE-770 (Allocation of Resources Without Limits)
**Tag:** Verified locally (bypass by rotating the client key); Reasoned for Vercel (multi-instance behavior).

The only thing that limits writes is `hits`, a module-level `Map`. The code comment admits the limit is per instance. On Vercel, Fluid Compute runs several instances across regions and resets them on cold start and redeploy. The key is the client IP, and an IPv6 client controls a whole /64, so it can present effectively unlimited addresses. Nothing at the DB level caps how many rows get written. Each row is about 0.6 to 1 KB plus index.

**Failure scenario:** a script POSTs valid builds from rotating IPv6 addresses (or from a few hundred IPv4 proxies at 10/min each). The Supabase free tier's 500 MB fills in hours to days. Supabase then puts the project into read-only mode, and saves fail for everyone. No credentials are needed, and the payload is the same JSON the app sends.

Locally, with 12 POSTs carrying a different `X-Forwarded-For` each, none were limited (`400 x12`). With a fixed XFF, requests 11 and 12 returned `429`.

**Fix (pick one, smallest first):**

1. Global cap in the DB, no new dependency. This is the backstop that holds no matter how many instances run:

   ```sql
   -- 0002_builds_insert_cap.sql
   create index builds_created_at_idx on public.builds (created_at);

   create function public.builds_insert_cap() returns trigger
   language plpgsql set search_path = '' as $$
   begin
     if (select count(*) from public.builds where created_at > now() - interval '1 hour') >= 1000 then
       raise exception 'builds insert cap reached' using errcode = 'P0001';
     end if;
     return new;
   end $$;

   create trigger builds_insert_cap before insert on public.builds
     for each row execute function public.builds_insert_cap();
   ```

   Map `P0001` in `createBuild` to a dedicated error, and return `429 rate_limited` from the route. The trade-off is that an attacker can block saves for everyone for up to an hour, but can no longer fill the database. Pick N from expected traffic.
2. Add a Vercel Firewall rate-limit rule on `POST /api/builds` (configured in the dashboard, no code). It works across instances and regions. Check which rate-limit rules your plan includes.
3. Replace the `Map` with a shared store (Upstash Ratelimit or Vercel KV), keyed on the IPv4 address or the IPv6 /64.

Also consider an occasional cleanup job (for example, delete builds older than N months that were never opened) if storage matters to you.

**Verification:** with the trigger in place and N set to 5 on a dev project, the 6th POST within an hour returns 429 and `select count(*)` stays at 5.

### 2. [Low] No security headers; framework banner exposed

**File:** `next.config.ts:3-15` (no `headers()`, no `poweredByHeader: false`)
**CWE:** CWE-693, CWE-1021
**Tag:** Verified (`curl -I` against `next start`).

The responses for `/`, `/garage` and `/b/<slug>` carry none of these: `Content-Security-Policy`, `X-Frame-Options` / `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`. They do carry `X-Powered-By: Next.js`.

I'm rating this Low on purpose. React escapes every place user data reaches the page (finding-free; see "Done well"), and the only clickjackable action is "save a build", which costs the victim nothing. A CSP here is defense in depth for a future regression, not a fix for a live bug. It is still the most valuable cheap change before deploy.

**Failure scenario:** if a future change adds a `dangerouslySetInnerHTML`, a JSON-LD `<script>` or a markdown renderer fed by `name`, nothing stops an injected script. Separately, any site can frame `/garage`.

**Fix: tested CSP.** I enforced the policy below through a header-injecting proxy in front of the production build (`next start`) and loaded `/`, `/garage`, `/garage?from=<slug>`, the full save flow and `/b/<slug>` with hostile names in headless Edge. Every page hydrated, WebGL rendered (R3F canvas plus drei `Environment`/`Html`/`Line`), all next/font files loaded (6 to 7 faces), the no-flash theme script applied the stored theme, and the save POST succeeded. The only violation reports were zod's `eval` feature probe (see #11), which is caught and harmless.

```ts
// next.config.ts
import type { NextConfig } from "next";

const isDev = process.env.NODE_ENV === "development";

// 'unsafe-inline' on script-src: Next streams the RSC payload in inline <script> tags whose content
// changes per build page, so hashes can't work, and nonces force every page to render dynamically
// (no static / PPR shell). React's escaping is the primary XSS control; this CSP still blocks
// external script hosts, plugins, <base> hijack, framing and off-origin fetches.
const csp = [
  "default-src 'self'",
  `script-src 'self' 'unsafe-inline'${isDev ? " 'unsafe-eval'" : ""}`,
  "style-src 'self' 'unsafe-inline'", // React style={} props are serialized as style="" attributes in SSR HTML
  "img-src 'self' blob: data:",
  "font-src 'self'", // next/font/google self-hosts the files under /_next/static/media
  `connect-src 'self'${isDev ? " ws:" : ""}`, // dev HMR uses a websocket
  "worker-src 'self' blob:",
  "object-src 'none'",
  "base-uri 'self'",
  "form-action 'self'",
  "frame-ancestors 'none'",
].join("; ");

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  poweredByHeader: false,
  async headers() {
    return [
      {
        source: "/:path*",
        headers: [
          { key: "Content-Security-Policy", value: csp },
          { key: "X-Frame-Options", value: "DENY" },
          { key: "X-Content-Type-Options", value: "nosniff" },
          { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
          { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=(), browsing-topics=()" },
          { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains" },
        ],
      },
    ];
  },
  turbopack: { /* unchanged */ },
};
```

Notes:
- **Do not add a `sha256-` hash for the theme script alongside `'unsafe-inline'`.** When a hash or nonce is present, browsers ignore `'unsafe-inline'`, and Next's inline RSC scripts would then be blocked.
- **HSTS:** I could not confirm Vercel's default HSTS from its docs, so the header is set explicitly above. After the first deploy, run `curl -sI https://<domain>/ | grep -i strict` to confirm. Add `preload` only after every subdomain serves HTTPS, because preload is hard to undo.
- **`upgrade-insecure-requests`** is left out on purpose. Every URL is relative and HSTS covers the upgrade, and it breaks `next start` on `http://localhost`.
- **A strict nonce CSP** (the `proxy.ts` recipe in `node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`) is possible but turns `/` and `/garage` into per-request renders. That is not worth it for this threat model.
- **Re-test after changing the policy:** `npm run build && npm run start`, open `/garage` with the DevTools console open, save a build, open `/b/<slug>`, and confirm there are no CSP errors other than the zod probe.

### 3. [Low] Rate-limit key derivation: spoofable off Vercel, shared fallback bucket, O(n) sweep

**File:** `src/app/api/builds/route.ts:54`, `:16`
**CWE:** CWE-348 (Use of Less Trusted Source), CWE-400
**Tag:** Verified on `next start`; Vercel behavior is from Vercel's docs.

```ts
const ip = req.headers.get("x-forwarded-for")?.split(",")[0].trim() || req.headers.get("x-real-ip") || "unknown";
```

- **On Vercel this is fine.** Vercel's request-headers doc says it overwrites `x-forwarded-for` and does not forward external IPs, to prevent spoofing. **Anywhere else** (`next start`, Docker, a VPS, or another proxy in front of Vercel), the client sets the key. Verified: rotating XFF values never hit 429.
- **Requests without XFF or X-Real-IP share one `"unknown"` bucket.** Verified: requests 11 and 12 without the header got 429. Behind a proxy that strips the header, one user locks out everyone.
- **The sweep on line 16 only runs once `hits.size > 10_000`, and it only removes expired entries.** If more than 10k distinct keys arrive within 60 s (trivial with a spoofed XFF off Vercel), every request then walks the whole map. That costs CPU, and the map grows without bound inside the window.

**Fix:** keep the code if Vercel is the only host, and add a comment saying the key is only trustworthy on Vercel. For portability, read `x-vercel-forwarded-for` first, and if no trusted header is present, do not use a shared constant: either skip the per-IP limit and rely on the global cap from #1, or reject with 400. Fix #1 makes this mostly moot.

### 4. [Low] `name`/`builder` accept control, bidi and invisible characters; NUL causes a 500

**Files:** `src/lib/build-schema.ts:54-55`, `supabase/migrations/0001_builds.sql:16-17`
**CWE:** CWE-20, CWE-451 (UI misrepresentation)
**Tag:** Verified (the API accepts them; render and `<title>` checked with curl). The 500 on NUL was reproduced against a PostgREST mock that mimics Postgres; reasoned for real Postgres, which rejects `\u0000` in `text` (SQLSTATE 22P05).

`z.string().trim().min(1).max(60)` accepts the following:
- `"​"` (zero-width space): a build that renders with a blank title. Verified: it passes validation (the request reached the backend step).
- `"‮evil.com"` (right-to-left override): the title text appears reversed on `/b/<slug>`, in `<title>` (verified raw in HTML), and in link previews. That allows mild impersonation in shared links.
- `"a\u0000b"`: passes zod, then Postgres rejects it, so the handler returns `500 internal_error` and logs `console.error` with the DB message. Not exploitable, but it is log noise and a 500 for bad input.
- Newlines and tabs go into `<title>` and the description meta.

**Fix:**

```ts
// build-schema.ts
// control chars (incl. NUL/newline), zero-width space, LRM/RLM, bidi embeddings/overrides/isolates, BOM
const SAFE_TEXT = /^[^\p{Cc}​‎‏‪-‮⁦-⁩﻿]*$/u;

export const CreateBuildSchema = z.object({
  name: z.string().normalize("NFC").trim().min(1).max(60).regex(SAFE_TEXT),
  builder: z.string().normalize("NFC").trim().max(40).regex(SAFE_TEXT).optional(), // "" still maps to null in createBuild
  config: BuildConfigSchema,
}).strict();
```

Leave ZWJ (U+200D) allowed so emoji sequences keep working. As a DB backstop, add `check (name !~ '[[:cntrl:]]')` (and the same for `builder`).

**Verification:** POST names `"\u0000"`, `"‮abc"` and `"​"`. Each should now return 400 `invalid_build`, and `"Café 🏍️"` should still return 201.

### 5. [Low] Saved builds are search-indexable and can't be taken down; API JSON cached `immutable` for a year

**Files:** `src/app/b/[slug]/page.tsx:37-43`, `src/app/api/builds/[slug]/route.ts:13-14`, migration (no delete path)
**CWE:** none directly (abuse handling / content moderation)
**Tag:** Verified (headers and `robots` meta via curl).

- `generateMetadata` sets `robots: { index: false }` only for missing or broken builds. Real builds are indexable, so anyone can publish a page on your domain with 100 characters of their own text (name plus builder) in `<title>` and `<h1>`. That is a small SEO-spam or harassment surface. It also means a user's "unlisted" build can show up in Google once a link to it is posted publicly.
- There is no way to remove a build except a manual SQL `delete`. After deletion, `/b/<slug>` updates right away (verified: `Cache-Control: private, no-cache, no-store`), but `GET /api/builds/<slug>` was served with `public, max-age=31536000, immutable`. Browsers, and any shared cache that honors `max-age`, keep serving the deleted build's JSON for up to a year. The code comment "builds are never updated" is true, but deletion is still a change.

**Fix:**

```ts
// page.tsx generateMetadata, ok branch
return { title: `${name} | Just a custom`, description: ..., robots: { index: false } };
```

```ts
// [slug]/route.ts
return Response.json(build, { headers: { "Cache-Control": "public, max-age=3600" } });
```

Write down the takedown procedure for later (`delete from public.builds where slug = '...'`). In the UI or README, say that "anyone with the link can see the build".

### 6. [Low] Read endpoints are unthrottled; each unknown slug costs a DB query

**Files:** `src/app/api/builds/[slug]/route.ts:7-12`, `src/app/b/[slug]/page.tsx:20-23`, `src/lib/builds.ts:44-48`
**CWE:** CWE-770
**Tag:** Reasoned.

Enumeration is not realistic: the slug space is 36^10, about 3.7e15. But every well-formed slug that doesn't exist does one indexed `select` on Supabase plus one function invocation. With the 404 set to `no-store` and the page set to `no-store`, nothing is cached. A sustained flood costs Vercel invocations and Supabase egress or CPU, but it can't read anything.

**Fix:** none needed in code now. If it ever shows up in usage, add a Vercel Firewall rate-limit rule on `/api/builds/*` and `/b/*`. Do not cache 404s publicly, or you'll pin "not found" for builds that get created later.

## Database (`supabase/migrations/0001_builds.sql`)

**[Reasoned]**. I can't reach your Supabase project. To confirm once the migration is applied, use the anon key, which is public on Supabase by design:

```bash
curl -s "https://<ref>.supabase.co/rest/v1/builds?select=*" -H "apikey: <anon>" -H "Authorization: Bearer <anon>"
# expect 401/403 "permission denied for table builds", NOT [] and NOT rows
curl -s -X POST "https://<ref>.supabase.co/rest/v1/builds" -H "apikey: <anon>" -H "Authorization: Bearer <anon>" \
  -H "content-type: application/json" -d '{"slug":"aaaaaaaaaa","name":"x","config":{}}'
# expect 401/403
```

- **RLS:** enabled, with no policies, and `revoke all … from anon, authenticated`. That is two independent denials: without a grant PostgREST and pg_graphql refuse, and even if a grant came back (for example via Supabase default privileges in a future migration), RLS without policies returns nothing. `service_role` bypasses both, which is intended.
- **Check constraints** match the zod schema (slug regex, name 1 to 60, builder 1 to 40 or null) and add a jsonb size cap (`octet_length(config::text) <= 4096`, about 10x a real config). `char_length` counts code points, while zod `.max()` counts UTF-16 units, so zod is the stricter of the two and the DB can never reject what zod accepted for length.
- No sequence is exposed (uuid pk), and `id` is never selected or returned (`COLUMNS` in `builds.ts:11`).
- **Gap:** no row-count cap. See #1.

## What is already done well (keep it)

- **Service-role key isolation:** server-only env name, `import "server-only"` guards, a single lazy client (`supabase/server.ts`), and a 503 when env is missing instead of a crash. Verified absent from client chunks.
- **DB access model:** RLS plus revoked grants, everything goes through the server, and lookups are only by unguessable slug. The reasoning is written down in the migration header, which is exactly right for a no-accounts app.
- **Strict validation at the trust boundary:** `.strict()` on every object, enums for every part, a hex regex for colors, `version: z.literal(1)`. Mass assignment (`slug`, `created_at`, `__proto__`) is rejected (verified 400). The server picks the slug and timestamps.
- **The DB is treated as untrusted on read:** `RowSchema.parse` in `builds.ts:14-20`, and a corrupted row degrades to a message instead of a broken render.
- **Body cap that can't be bypassed:** the Content-Length pre-check plus a streaming byte counter. Verified: 20 KB with Content-Length → 413, 20 KB chunked without Content-Length → 413, 9 KB of whitespace padding → 413, Content-Length combined with Transfer-Encoding → 400 from Node, a non-numeric Content-Length → 400 from Node.
- **Ordering in `POST`:** the content-type check (415), then the rate limit, then the capped read, then `JSON.parse`, then zod, then the DB. Cheap rejections come first, and the 415 check also rules out form-based cross-site posts (moot without cookies, but correct).
- **Method handling:** GET on the collection, and PUT/DELETE → 405. OPTIONS → 204 with no CORS headers, so cross-origin browser calls are blocked. Verified.
- **Slugs:** nanoid `customAlphabet` (CSPRNG), about 51.7 bits, validated by the same regex on the client (`GarageApp.tsx:14`), on the server (`builds.ts:8`) and in the DB check, with collision retry on 23505. `?from=` is regex-checked before it is put into a fetch path, so there is no path injection.
- **XSS:** no user data reaches `dangerouslySetInnerHTML`. Verified by actually saving and rendering `</script><script>alert(1)</script>`, `"><img src=x onerror=alert(2)>` and `<svg/onload=alert(3)>`. They come out entity-escaped in `<h1>` and `<title>`, and `<`-escaped in the inline RSC payload. No JavaScript dialog fired in headless Edge. Color hex values go through a regex before reaching `style={{ background }}`.
- **Theme no-flash script** (`layout.tsx:41`): a static string with no interpolation, which only accepts the exact values `"light"` and `"dark"` from storage.
- **localStorage draft:** `JSON.parse` inside try/catch, then the strict `BuildConfigSchema`, discarded silently on failure. `__proto__` keys can't pass `.strict()`. Verified no prototype pollution with a poisoned draft in Edge.
- **No open redirect:** the only navigations are the constant `router.replace("/garage")` and links built from validated slugs. `?style=` is checked against `STYLES`.
- **Clipboard/share:** only a same-origin URL built from the saved slug.
- **404s:** the API 404 is `no-store`, and missing or broken build pages are `noindex`. Error responses never include DB messages; those go only to the server log.
- **No third-party runtime fetches:** fonts are self-hosted by next/font, the 3D scene uses local Lightformers instead of an HDR CDN, and there are no analytics. That is why a tight `connect-src 'self'` CSP works.
