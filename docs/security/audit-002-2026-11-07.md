## Findings

### 1. Low: `SAFE_TEXT` misses some invisible and bidi characters (existed before this change)

- File: `src/lib/build-schema.ts:153`
- Status: **Verified** (fuzz script)
- Not a regression: the regex is identical at HEAD. It is reported here because the fuzz run found it.

The regex is a denylist. It blocks `\p{Cc}`, ZWSP, LRM/RLM, the bidi embedding and override ranges, the isolate range and BOM. The fuzz run shows these characters still get through in `name` and `builder`:

- U+061C ARABIC LETTER MARK, a bidi control in the same class as the LRM/RLM that are already blocked
- U+2028 and U+2029, the line and paragraph separators
- U+00AD, the soft hyphen

By reading the regex (**Reasoned**), U+2060 to U+2064, U+180E and the tag characters U+E0000 to U+E007F would also pass.

Scenario: a saved build whose name contains U+061C or U+2028 can reorder or hide part of the title on `/b/<slug>` and in the browser tab title. This is display spoofing only. React escapes the text, so it cannot become script.

Fix: block the whole format category and keep only ZWJ: `const SAFE_TEXT = /^(?:‍|[^\p{Cc}\p{Cf}\p{Zl}\p{Zp}])*$/u;`. I checked this regex: it accepts `a`, `café` and an emoji ZWJ sequence, and rejects U+061C, U+2028, U+00AD, U+202E and a BOM in the middle of a string (**Verified**). Add these characters to `build-schema.test.ts`.

### 2. Info: `jac:debug3d` debug hook ships in production

- File: `src/three/Scene.tsx:50-63`
- Status: **Reasoned**

When `localStorage["jac:debug3d"] === "1"`, every canvas mount appends its R3F `RootState` to `window.__jac3d`, and the array is never trimmed. Only the visitor can set the flag, so there is no cross-user risk. The only effect is a memory leak across remounts while the flag is on, plus an extra global for anyone who already has script access.

Fix (optional): wrap the hook in `process.env.NODE_ENV !== "production"`, or keep only the latest state (`__jac3d = [state]`).

### 3. Info: catalog name maps are plain objects with prototypes, so they depend on the schema for safety

- File: `src/lib/catalog.ts:69` (`OPTION_NAMES: Record<string, string>`), also `STYLE_NAMES`, `BASE_NAMES`, `FINISH_NAMES`, `PRESETS`, `CLASHES`
- Status: **Verified** that it is safe today. **Reasoned** for the future risk.

`specRows`, `describeBuild`, `generateMetadata` and the spec sheet look up display strings with keys read from the DB. Today every key is checked against a zod enum first, both on write (`CreateBuildSchema`) and on read (`RowSchema` in `getBuild`). The fuzz confirms that `__proto__`, `constructor`, `toString` and similar values are rejected at every level, and that every enum value has a display name.

The risk is a future refactor that renders a key before validating it. `OPTION_NAMES["constructor"]` would then return `Object`'s constructor function, and React would throw when rendering it.

Fix (optional): build these maps with `Object.assign(Object.create(null), {...})`, or look up with `Object.hasOwn(map, k) ? map[k] : k`. The current schema-first order is correct, so this is defense in depth only.

## Checks run

### 1. Validation (Verified)

The script is `fuzz.mts` in the session scratchpad. It imports `src/lib/build-schema.ts` and `catalog.ts` with `node --experimental-strip-types`. 137 cases; the one "failure" was a test-expectation mistake, explained in the last bullet.

- **Extra keys** (`extra`, `__proto__`, `constructor`, `prototype`, `toString`) were injected through `JSON.parse`, the same way the API parses bodies, at the root, `config`, `config.parts` and `config.paint`, for both v1 and v2. All were rejected. `.strict()` holds at every level, including both union branches.
- **Prototype-ish values** as `parts.frame`, `style`, `base` or `finish` were all rejected. `Object.prototype` was not polluted.
- **Each of the 25 part keys missing** was rejected.
- **v1 smuggling:** a v1 body with a v2-only style (`chopper`), finish (`candy`) or frame (`softail`), or with an added `base` or `headlamp` field, was rejected. A v2 body tagged `version: 1` and a v1 body tagged `version: 2` were rejected. `version` values `3`, `0`, `"2"`, `null` and `2.0000001` were rejected.
- **v1 to v2 transform:** I ran all 52,488 v1 combinations (styles × parts × finishes) through `BuildConfigSchema`. Every output parsed again as an identical v2 config, so the transform always produces valid v2.
- **Random mutation:** 20,000 mutated v1 and v2 configs gave 575 accepted outputs, and none had a value outside the v2 enums.
- **Hex:** `#fff`, `red`, `#000000;background:url(x)`, a trailing newline, a leading space, `url(javascript:1)` and 7-digit values were all rejected. The anchored `^#[0-9a-fA-F]{6}$` regex holds.
- **Size:** the largest possible v2 config is 720 B as compact JSON and about 785 B as `jsonb::text`. The DB check of `octet_length(config::text) <= 4096` therefore has about 5x headroom. The largest valid POST body is about 954 B against the 8 KB cap. `MAX_BODY_BYTES`, `readCapped`, the 415 content-type check and the `fields`-only error response are unchanged in `src/app/api/builds/route.ts`.
- **Name and builder:** NUL, newline, RLO, ZWSP, LRI, NEL, LRM and over-length values were rejected, and `builder: null` was rejected. A leading BOM is accepted only because `.trim()` removes it before the regex runs; the stored value is `"a"`, and a BOM in the middle is rejected. See finding 1 for the gaps.

### 2. Rendering untrusted data (Verified and Reasoned)

- `getBuild` runs `RowSchema`, which includes the full v2 or upgraded v1 union, on every DB read. `/b/[slug]` maps a `ZodError` to the "data rusak" message (`page.tsx:28`), so a garbage row never reaches `specRows`.
- **Verified:** 2,000 random valid configs produced no `undefined` labels in `specRows` or `describeBuild`, and `clashesFor`, `presetFor` and `partsForBase` never threw.
- The only `dangerouslySetInnerHTML` is the constant theme script in `layout.tsx:47`, which is unchanged. There is no `innerHTML` or `eval`. `ScreenLabel` sets `cssText` from a constant only.
- **Paint hex** reaches `style={{ background }}` (`page.tsx:149`, `Rail.tsx:274`) and `THREE.Color.set` (`Bike.tsx:185`) only after passing the anchored hex regex. The Rail text input re-checks with `HEX_RE` before committing (`Rail.tsx:240`). React serializes `style` values as properties, so `;` injection would not work even without the regex.
- **Links:** `href`s are built only from a regex-checked slug, or from catalog ids in `Landing.tsx`. There are no `_blank` targets and no `window.open`.

### 3. Client storage (Verified in headless Edge)

I seeded hostile values and reloaded `/garage`:

- `jac:draft:v1` was set to `{style:"__proto__", parts:{"__proto__":{...}}, paint.tank:"red;background:url(//evil…)"}`. `readDraft` (try/catch plus `safeParse`) discarded it, the garage loaded `DEFAULT_BUILD`, and autosave overwrote the bad draft. There was no exception and no request to another origin.
- `jac:quality` was set to `<img src=x onerror=alert(1)>`. `compute()` accepts only `auto`, `high` or `low`, so the UI showed "Otomatis". The value is never rendered.
- `jac:tour:v1` was set to garbage. Only `=== "done"` counts, so the tour is offered again, which is harmless.
- Every read and write is in try/catch (`GarageApp.tsx:19,86`, `stage-store.ts:75,96`, `Tour.tsx:52,59`, `Scene.tsx:54`).
- `?style=__proto__` falls through the `STYLES.includes` check to the draft or default build. `?from=` is regex-checked before the fetch, and the fetched config is parsed again with `safeParse`.
